3주차 학습 아티클: 라우팅, 렌더링, Context API와 개발 환경 설정

작성 안내: 아래 실습 부분은 제공 코드에 맞춘 초안입니다. PRACTICE_GUIDE.md 순서대로 실제 실행한 뒤 사용하고, 실행 결과나 느낀 점이 다르면 본인 경험에 맞게 수정하세요.

1. 동적 라우팅, 중첩 라우팅, 쿼리 파라미터와 URL 파라미터

라우팅은 현재 URL에 맞는 화면을 보여주는 것이다. 동적 라우팅은 /tasks/:taskId처럼 주소 일부를 변수로 받아 같은 컴포넌트에서 서로 다른 데이터를 보여주는 방식이다. 예를 들어 /tasks/3에서 taskId는 3이 되며 useParams로 읽을 수 있다.

중첩 라우팅은 부모 라우트 안에 자식 라우트를 두는 구조이다. 부모 화면에서 공통으로 보여줄 메뉴나 통계를 배치하고 Outlet 위치에 자식 페이지를 표시할 수 있다. 이번 코드에서는 Layout에 제목과 메뉴를 두고 Outlet에 할 일 목록, 완료 목록 또는 통계 화면을 표시하도록 구성했다.

URL 파라미터라는 말은 넓은 의미로 쓰이기도 하지만, 여기서는 /tasks/3의 3처럼 경로에 들어가는 값을 뜻한다. 쿼리 파라미터는 /tasks?filter=completed&page=2처럼 물음표 뒤에 들어가는 값이다. 경로 파라미터는 주로 특정 대상을 구분하고, 쿼리 파라미터는 필터나 정렬, 페이지 번호와 같은 옵션을 표현할 때 사용한다. 쿼리 파라미터는 useSearchParams로 읽거나 변경할 수 있다. 이번 Todo 앱에는 정적인 경로와 중첩 라우팅을 적용했고, /tasks/:taskId와 쿼리 파라미터는 개념을 설명하기 위한 예시이다.

2. useEffect와 useLayoutEffect의 차이

두 Hook은 렌더링 결과가 DOM에 반영된 이후 외부 시스템과 동기화하거나 추가 작업을 할 때 사용할 수 있다. 다만 화면이 그려지는 시점과의 관계가 다르다. useEffect는 일반적으로 브라우저가 화면을 그린 뒤 실행되며, 이벤트에 의해 발생한 Effect는 그리기 전에 실행될 수도 있다. 따라서 항상 화면이 그려진 뒤라고 단정하면 안 된다.

useLayoutEffect는 DOM이 반영된 뒤 브라우저가 화면을 그리기 전에 실행된다. 요소의 크기나 위치를 측정하고 그 결과로 화면을 수정해야 할 때 사용할 수 있다. 다만 실행과 그 안의 상태 갱신이 화면 그리기를 막을 수 있어 꼭 필요한 경우에 사용해야 한다.

이번 과제의 localStorage 저장은 요소 크기를 측정할 필요가 없으므로 useEffect를 사용했다. 의존성 배열에 tasks를 넣어 목록이 바뀌면 저장되도록 했다. 초기 목록은 useState의 초기화 함수에서 불러와 빈 배열이 저장된 목록을 먼저 덮어쓰지 않게 했다. 초기화 함수는 개발 환경의 StrictMode에서 두 번 호출될 수 있으므로 읽기만 수행하도록 작성했다.

3. 브라우저 렌더링 과정

브라우저는 HTML을 읽어 DOM을 만들고 CSS를 읽어 CSSOM을 만든다. 이후 화면에 표시할 요소와 스타일 정보를 바탕으로 렌더 트리를 구성한다. Layout 단계에서는 각 요소의 크기와 위치를 계산하고, Paint 단계에서는 글자, 배경, 테두리 같은 시각 정보를 그리기 위한 작업을 수행한다. 이후 래스터화와 합성 등의 과정을 거쳐 최종 화면이 표시된다.

이는 이해를 위한 대표적인 흐름이며 모든 변경이 이 과정을 처음부터 끝까지 다시 실행하는 것은 아니다. 변경된 속성과 브라우저의 최적화에 따라 필요한 단계만 수행될 수 있다.

4. Reflow와 Repaint

Reflow는 요소의 크기나 위치와 같은 배치 정보를 다시 계산하는 작업으로, Layout과 연결되는 개념이다. 예를 들어 요소의 너비를 바꾸거나 목록에 항목을 추가하면 주변 요소의 위치까지 다시 계산해야 할 수 있다.

Repaint는 배치가 그대로인 상태에서 색상이나 배경처럼 화면의 시각적인 부분을 다시 그리는 작업이다. 배경색을 바꾸는 경우에는 보통 Layout 없이 Paint가 필요하다. Reflow가 일어나면 이후 Paint도 필요한 경우가 많다. 반면 transform이나 opacity 애니메이션은 조건에 따라 합성 단계에서 처리될 수 있으므로 모든 스타일 변경을 Reflow나 Repaint로만 설명할 수는 없다.

5. Context API 실습

이번 실습에서는 Todo 앱의 할 일 목록을 여러 컴포넌트에서 공유하도록 Context API를 적용했다. 이전처럼 작업 데이터를 중간 컴포넌트마다 props로 전달하는 대신 TasksProvider에서 목록과 변경 함수를 관리하도록 구성했다.

먼저 TasksContext.js에서 createContext(null)로 Context를 만들었다. TasksProvider.jsx에서는 useState로 tasks를 관리하고 추가, 수정, 삭제, 완료 상태 변경 함수를 만들었다. 이 값들을 Provider의 value로 전달하고, main.jsx에서 App을 TasksProvider로 감쌌다. Provider는 Routes 바깥에 두어 페이지를 이동해도 같은 상태를 사용하도록 했다.

useTasks라는 사용자 정의 Hook 안에서 useContext를 호출하도록 구성했다. TodoList는 여기서 목록과 수정 함수를 가져오고, TodoStats는 같은 Context에서 전체 개수, 진행 중 개수, 완료 개수, 완료율을 가져온다. 목록에서 체크박스를 누르면 공유 상태가 바뀌기 때문에 목록과 통계가 함께 갱신되는 구조이다.

Context 자체가 데이터를 영구 저장하는 것은 아니다. 새로고침 이후에도 데이터를 유지하기 위해 localStorage를 별도로 사용했다. 저장할 때는 JSON.stringify로 배열을 문자열로 바꾸고, 불러올 때는 JSON.parse로 다시 배열로 변환했다. 완료율은 완료 개수를 전체 개수로 나눈 뒤 100을 곱해 계산했고, 전체 개수가 0이면 0%가 되도록 처리했다.

실습에서는 작업 두 개를 추가하고 한 개를 완료한 뒤 전체 2개, 진행 중 1개, 완료 1개, 완료율 50%가 표시되는지 확인하면 된다. /completed로 이동했을 때 완료한 작업만 나타나고 새로고침 후에도 내용이 유지되는지도 확인한다. 이 과정을 통해 컴포넌트 간 상태 공유와 새로고침 이후 데이터 저장은 서로 다른 역할이라는 점을 구분할 수 있었다.

6. Tailwind CSS 설치 및 설정

이번 프로젝트는 Tailwind CSS v4 방식으로 설정했다. tailwindcss와 @tailwindcss/vite를 개발 의존성으로 설치하고 vite.config.js의 plugins에 기존 react()와 함께 tailwindcss()를 등록했다. global.css 첫 줄에는 @import "tailwindcss";를 추가하고 main.jsx에서 CSS 파일을 불러오도록 했다.

이후 통계 카드와 메뉴에 grid, grid-cols-3, flex, items-center 같은 유틸리티 클래스를 적용했다. 세부 색상과 간격 및 모바일 화면은 global.css에 정의했다. 모든 기존 CSS를 한꺼번에 바꾸지는 않았고, 2주차의 입력창과 개별 작업 스타일은 기본 CSS를 유지했다.

v3 설정 예제에 나오는 npx tailwindcss init -p 명령은 이번 v4 Vite 설정에서는 사용하지 않았다. 설치만 하는 것과 실제 스타일이 적용되도록 Vite 및 CSS를 연결하는 것은 별도의 단계라는 점을 알게 되었다.

7. ESLint 설치 및 설정

ESLint는 코드를 실행하기 전에 정의되지 않은 변수, 사용하지 않는 변수, React Hook 사용 규칙 등의 문제를 검사하는 도구이다. 이번 코드는 ESLint 9 기반으로 구성하고, eslint.config.js에 검사 대상 파일과 추천 규칙을 설정했다. React Hook과 Fast Refresh 관련 플러그인을 함께 사용하고 node_modules와 dist는 검사에서 제외했다.

eslint-config-prettier를 설정 배열 마지막에 두어 Prettier와 충돌하는 스타일 규칙을 끄도록 했다. package.json의 lint 스크립트는 eslint .로 설정해 npm.cmd run lint로 검사할 수 있게 했다. JSX에서 사용하는 대문자 컴포넌트 이름이 기본 unused 검사에서 잘못 보고되지 않도록 관련 이름 패턴을 예외 처리했다. 이 설정은 모든 종류의 미사용 컴포넌트를 완벽하게 검출하는 구성은 아니라는 점도 구분했다.

8. Prettier 설치 및 설정

Prettier는 들여쓰기, 따옴표, 줄바꿈 등의 코드 형식을 자동으로 통일하는 도구이다. prettier와 eslint-config-prettier를 개발 의존성으로 설치하고 .prettierrc에 작은따옴표 사용, 세미콜론 사용, trailingComma와 printWidth를 설정했다.

.prettierignore에는 node_modules, dist, package-lock.json을 넣었다. package.json에 format과 format:check 스크립트를 등록하여 npm.cmd run format으로 형식을 수정하고 npm.cmd run format:check로 형식이 맞는지 확인하도록 했다. ESLint는 코드 규칙을 검사하고 Prettier는 형식을 정리하는 역할이므로 두 도구의 목적을 구분해서 사용했다.

9. React Router 설치 및 설정

react-router를 설치하고 main.jsx에서 BrowserRouter로 앱을 감쌌다. App.jsx에는 Routes와 Route를 사용해 /는 전체 할 일, /active는 진행 중인 할 일, /completed는 완료 목록, /stats는 통계를 보여주도록 설정했다.

공통 Layout에 할 일 목록·통계 탭과 완료 목록 링크를 만들고 Outlet 위치에 페이지 내용을 표시했다. 활성화된 링크에는 다른 색상을 적용해 현재 페이지를 알 수 있게 했다. 페이지를 이동할 때 전체 문서를 다시 요청하지 않고 URL에 맞는 컴포넌트를 렌더링하며, 브라우저 뒤로 가기로 이전 페이지에 돌아갈 수도 있다.

실제 서버에 배포할 때에는 /completed 주소를 직접 열어도 index.html이 반환되도록 SPA fallback 설정이 필요하다. 이번 제출은 Vite 개발 서버에서 동작을 확인하는 구성이며 GitHub 저장소에 코드를 push하는 것 자체가 웹사이트 배포를 의미하지는 않는다.
