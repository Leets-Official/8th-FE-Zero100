# [2주차] JS와 React

## 1. JS 싱글 스레드 언어이며 비동기 언어인 이유

JavaScript는 **싱글 스레드(Single Thread)** 기반의 언어로, 하나의 **Call Stack**에서 한 번에 하나의 작업을 처리한다. 함수는 **LIFO(Last In First Out)** 방식으로 실행된다.

하지만 **Web API, Task Queue, Event Loop**를 통해 비동기 처리가 가능하다.

예를 들어 `setTimeout()`과 같은 작업은 Web API에서 처리되고, 작업이 완료되면 Callback이 Task Queue로 이동한다. 이후 Event Loop가 Call Stack이 비어 있는지 확인하고 Callback을 Call Stack으로 이동시켜 실행한다.

Call Stack
↓
Web API
↓
Task Queue
↓
Event Loop
↓
Call Stack

따라서 JavaScript는 싱글 스레드로 동작하지만 Web API와 Event Loop 등을 통해 비동기 처리가 가능하다.

## 2. null과 undefined의 차이와 null이 object인 이유

### 2-1. null과 undefined의 차이

`undefined`와 `null`은 모두 값이 없음을 나타내지만, 사용되는 상황과 의미가 다르다.

| 구분         | `undefined`                | `null`                        |
| ------------ | -------------------------- | ----------------------------- |
| **의미**     | 값이 정의되지 않음         | 의도적으로 값이 없음을 나타냄 |
| **할당**     | JavaScript가 자동으로 할당 | 개발자가 직접 할당            |
| **`typeof`** | `"undefined"`              | `"object"`                    |

- `undefined`: 값을 할당하지 않았을 때 JavaScript가 자동으로 할당한다.
- `null`: 개발자가 값이 없음을 명시적으로 나타낼 때 사용한다.
- `null == undefined`는 `true`이지만, `null === undefined`는 `false`이다.

### 2-2. `null`이 object인 이유

`typeof null`의 결과는 `"object"`이다.

`null`은 실제로는 원시 타입이지만, JavaScript 초기 구현의 타입 판별 방식에서 발생한 역사적인 문제로 인해 `"object"`로 판별된다.

이 동작을 변경하면 기존 코드와의 하위 호환성 문제가 발생할 수 있기 때문에 현재까지 유지되고 있다.

## 3. 얕은 복사 vs 깊은 복사, 왜 상태를 직접 수정하면 안되는 이유

### 3-1. 얕은 복사와 깊은 복사

| 구분          | 얕은 복사 (Shallow Copy)                | 깊은 복사 (Deep Copy)                     |
| ------------- | --------------------------------------- | ----------------------------------------- |
| **복사 범위** | 가장 바깥쪽만 복사                      | 내부의 중첩된 값까지 모두 복사            |
| **참조**      | 중첩 객체는 원본과 같은 주소를 공유     | 원본과 완전히 독립된 주소를 가짐          |
| **원본 영향** | 중첩 객체 수정 시 원본도 변경될 수 있음 | 복사본을 수정해도 원본에 영향을 주지 않음 |
| **주요 방법** | `{ ...obj }`, `Object.assign()`         | `structuredClone()`, `cloneDeep()` 등     |

### 3-2. 상태를 직접 수정하면 안 되는 이유

React에서는 상태를 직접 수정하지 않고 **새로운 상태를 만들어 변경하는 방식**을 사용해야 한다.

상태를 직접 수정하면 다음과 같은 문제가 발생할 수 있다.

- **변경 감지 문제**: 기존 객체의 참조가 그대로 유지되어 상태 변경을 제대로 감지하지 못할 수 있다.
- **예측하기 어려운 데이터 변경**: 여러 곳에서 같은 데이터를 참조하면 의도하지 않은 변경이 발생할 수 있다.
- **디버깅 어려움**: 데이터가 언제, 어디서 변경되었는지 추적하기 어려워진다.

따라서 React에서는 **불변성(Immutability)을 유지하면서 새로운 객체를 만들어 상태를 변경하는 것**이 중요하다.

## 4. 라이브러리 vs 프레임워크

### 라이브러리 (Library)

라이브러리는 개발에 필요한 기능을 미리 만들어 놓은 **코드 모음**이다.

개발자가 필요한 기능을 선택하여 직접 호출하고 사용할 수 있으며, 어떤 라이브러리를 언제 사용할지 개발자가 결정한다.

### 프레임워크 (Framework)

프레임워크는 개발에 필요한 **기본적인 구조와 규칙을 제공하는 개발 틀**이다.

개발자는 프레임워크가 정해 놓은 구조와 규칙에 따라 코드를 작성해야 하며, 프레임워크가 개발자의 코드를 호출하여 실행한다.

### 공통점

라이브러리와 프레임워크 모두 다른 사람이 미리 작성해 둔 코드를 활용하여 **필요한 기능을 편리하게 구현할 수 있도록 도와준다.**

### 차이점

| 구분          | 라이브러리                       | 프레임워크                          |
| ------------- | -------------------------------- | ----------------------------------- |
| **제어 주체** | 개발자                           | 프레임워크                          |
| **사용 방식** | 필요한 기능을 개발자가 직접 호출 | 정해진 구조와 규칙에 따라 코드 작성 |
| **자유도**    | 비교적 자유롭게 사용 가능        | 정해진 규칙을 따라야 함             |

> **라이브러리:** 개발자가 필요할 때 호출  
> **프레임워크:** 프레임워크가 정해진 방식에 따라 개발자의 코드를 호출

## 5. DOM과 Virtual DOM 리액트의 가상 DOM에 대하여

### DOM (Document Object Model)

DOM은 웹페이지를 구성하는 HTML 요소들의 **구조를 객체 형태로 표현한 것**이다.

HTML 요소 하나하나를 **노드(Node)**라고 하며, 이러한 노드들이 트리 형태로 구성된 것을 **DOM Tree**라고 한다.

### Virtual DOM

Virtual DOM은 **실제 DOM의 구조를 JavaScript 객체 형태로 표현한 것**이다.

React에서는 `state`가 변경되면 새로운 Virtual DOM을 생성하고, 이전 Virtual DOM과 비교하여 변경된 부분을 찾는다. 이 과정을 **Diffing**이라고 한다.

이후 변경된 부분만 실제 DOM에 반영하여 화면을 업데이트한다.

### React의 Virtual DOM 동작 과정

State 변경
↓
새로운 Virtual DOM 생성
↓
기존 Virtual DOM과 비교
↓
변경된 부분 확인 (Diffing)
↓
실제 DOM에 반영
↓
화면 업데이트

## 6. CSR, SSR, SSG, ISR의 차이점에 대하여

웹 페이지를 브라우저에 어떻게 렌더링하는지에 따라 **CSR, SSR, SSG, ISR**로 나눌 수 있다.

### CSR (Client Side Rendering)

브라우저에서 JavaScript를 실행하여 **페이지를 렌더링하는 방식**이다.

처음에는 HTML을 받은 후 JavaScript를 실행하고 필요한 데이터를 가져와 화면을 구성한다.

- **장점**: 페이지 이동이 빠르고 사용자와의 상호작용에 유리하다.
- **단점**: 초기 로딩이 느릴 수 있고 SEO에 불리할 수 있다.

### SSR (Server Side Rendering)

사용자가 페이지를 요청할 때마다 **서버에서 HTML을 생성하여 전달하는 방식**이다.

- **장점**: 초기 화면을 빠르게 보여줄 수 있고 SEO에 유리하다.
- **단점**: 요청마다 서버에서 페이지를 생성해야 하므로 서버 부담이 커질 수 있다.

### SSG (Static Site Generation)

**빌드 시점에 HTML을 미리 생성해두는 방식**이다.

미리 생성된 페이지를 제공하기 때문에 서버에서 매번 HTML을 생성할 필요가 없다.

- **장점**: 빠른 페이지 응답과 높은 성능
- **단점**: 데이터가 자주 변경되는 페이지에는 적합하지 않다.

### ISR (Incremental Static Regeneration)

SSG처럼 정적으로 페이지를 생성하지만, **일정한 주기나 조건에 따라 페이지를 다시 생성하는 방식**이다.

- **장점**: 정적 페이지의 빠른 성능을 유지하면서 변경된 데이터를 반영할 수 있다.
- **단점**: 데이터가 즉시 변경되는 것은 아니므로 실시간성이 필요한 페이지에는 적합하지 않다.

### 차이점 정리

| 방식    | 렌더링 시점         | 특징                   |
| ------- | ------------------- | ---------------------- |
| **CSR** | 브라우저            | 클라이언트에서 렌더링  |
| **SSR** | 요청 시             | 서버에서 HTML 생성     |
| **SSG** | 빌드 시             | HTML을 미리 생성       |
| **ISR** | 빌드 후 주기적 갱신 | 정적 페이지를 업데이트 |

> **CSR** → 브라우저에서 렌더링  
> **SSR** → 요청할 때 서버에서 렌더링  
> **SSG** → 빌드할 때 미리 렌더링  
> **ISR** → 미리 렌더링하고 필요할 때 다시 생성

## 7. 본인이 프로젝트 초기 세팅한 방법

### 7-3. 작업 브랜치 생성

`npm create vite@latest . -- --template react`

### 7-5. 패키지 설치

프로젝트에 필요한 패키지를 설치하였다.

`npm install`

### 7-6. 개발 서버 실행

개발 서버를 실행하여 프로젝트가 정상적으로 동작하는지 확인하였다.

`npm run dev`

실행 후 `http://localhost:5173/`에서 프로젝트를 확인하였다.
