# [아티클] 3주차 공통과제

## 1. 동적 라우팅, 중첩 라우팅, 쿼리 파라미터, URL 파라미터

### 1-1. 동적 라우팅 (Dynamic Routing)

동적 라우팅은 URL의 일부를 변수처럼 처리하여 하나의 컴포넌트로 여러 페이지를 보여주는 방식이다.

예를 들어 게시글마다 상세 페이지가 존재한다면 각각의 Route를 따로 만드는 대신 다음과 같이 하나의 Route로 처리할 수 있다.

```jsx
<Route path="/posts/:id" element={<PostDetail />} />
```

위와 같이 설정하면 다음과 같은 주소를 하나의 `PostDetail` 컴포넌트로 처리할 수 있다.

```text
/posts/1
/posts/2
/posts/3
```

페이지의 구조는 같지만 URL에 따라 다른 데이터를 보여줘야 할 때 사용한다.

**주요 활용 사례**

- 게시글 상세 페이지
- 상품 상세 페이지
- 사용자 프로필 페이지

### 1-2. URL 파라미터 (URL Parameter / Path Parameter)

URL 파라미터는 URL 경로의 일부에 실제 값을 전달하는 방식이다. 동적 라우팅에서 `:id`와 같이 정의한 부분에 해당한다.

예를 들어 다음 URL에서 `123`은 URL 파라미터 값이다.

```text
/users/123
```

React Router에서는 `useParams()`를 사용하여 값을 가져올 수 있다.

```jsx
import { useParams } from 'react-router-dom';

function UserDetail() {
  const { id } = useParams();

  return <h1>사용자 ID: {id}</h1>;
}
```

Route는 다음과 같이 설정한다.

```jsx
<Route path="/users/:id" element={<UserDetail />} />
```

- `/users/123` → `id`는 `"123"`
- `/users/456` → `id`는 `"456"`

`useParams()`로 가져온 값은 기본적으로 문자열이다. 숫자로 계산해야 한다면 필요에 따라 숫자로 변환해야 한다.

**주요 활용 사례**

- 특정 게시글이나 상품 식별
- 사용자 프로필 조회
- 특정 데이터의 상세 페이지 표시

### 1-3. 쿼리 파라미터 (Query Parameter / Query String)

쿼리 파라미터는 URL의 `?` 뒤에 `키=값` 형태로 추가적인 조건을 전달하는 방식이다.

```text
/search?keyword=react&page=2
```

위 URL에는 다음과 같은 값이 포함되어 있다.

- `keyword` → `react`
- `page` → `2`

여러 값을 전달할 때는 `&`로 구분한다.

```text
/search?keyword=react&page=2&sort=latest
```

React Router에서는 `useSearchParams()`를 사용하여 값을 가져올 수 있다.

```jsx
import { useSearchParams } from 'react-router-dom';

function SearchPage() {
  const [searchParams] = useSearchParams();

  const keyword = searchParams.get('keyword');
  const page = searchParams.get('page');

  return (
    <div>
      <p>검색어: {keyword}</p>
      <p>페이지: {page}</p>
    </div>
  );
}
```

`/search?keyword=react&page=2`로 접근하면 `keyword`는 `"react"`, `page`는 `"2"`가 된다.

**주요 활용 사례**

- 검색어 전달
- 정렬 방식 지정
- 페이지네이션
- 카테고리 및 필터 설정

### 1-4. URL 파라미터와 쿼리 파라미터의 차이

| 구분              | URL 파라미터     | 쿼리 파라미터                 |
| ----------------- | ---------------- | ----------------------------- |
| 형태              | `/users/123`     | `/users?id=123`               |
| 위치              | URL 경로 내부    | `?` 뒤                        |
| 구분 방식         | `/` 사용         | `?`, `&` 사용                 |
| React Router Hook | `useParams()`    | `useSearchParams()`           |
| 주요 목적         | 특정 데이터 식별 | 검색, 필터, 정렬, 페이지 설정 |
| 예시              | `/products/123`  | `/products?category=shoes`    |

핵심 차이는 다음과 같다.

- **URL 파라미터**: 어떤 데이터를 보여줄지 식별하기 위한 값
- **쿼리 파라미터**: 데이터를 어떤 조건으로 보여줄지 결정하는 옵션 값

### 1-5. 중첩 라우팅 (Nested Routing)

중첩 라우팅은 부모 Route 안에 자식 Route를 구성하는 방식이다.

공통 레이아웃을 유지하면서 내부 콘텐츠만 변경해야 할 때 유용하다.

예를 들어 설정 페이지를 다음과 같이 구성할 수 있다.

```text
/settings
/settings/profile
/settings/security
```

React Router에서는 부모 Route 안에 자식 Route를 작성한다.

```jsx
<Route path="/settings" element={<Settings />}>
  <Route path="profile" element={<Profile />} />
  <Route path="security" element={<Security />} />
</Route>
```

부모 컴포넌트에서는 `<Outlet />`을 사용하여 자식 Route가 렌더링될 위치를 지정한다.

```jsx
import { Outlet } from 'react-router-dom';

function Settings() {
  return (
    <div>
      <Sidebar />
      <main>
        <Outlet />
      </main>
    </div>
  );
}
```

`/settings/profile`로 이동하면 `Settings`의 공통 레이아웃은 유지되고, `<Outlet />` 위치에 `Profile` 컴포넌트가 렌더링된다.

**주요 활용 사례**

- 설정 페이지
- 마이페이지
- 관리자 대시보드
- 공통 사이드바가 있는 페이지

### 1-6. 라우팅 방식 정리

| 방식          | 핵심 개념                           | 예시                |
| ------------- | ----------------------------------- | ------------------- |
| 동적 라우팅   | URL 일부를 변수처럼 처리            | `/posts/:id`        |
| URL 파라미터  | 경로에서 실제 값을 가져옴           | `useParams()`       |
| 쿼리 파라미터 | URL 뒤에 조건을 추가                | `useSearchParams()` |
| 중첩 라우팅   | 부모 레이아웃 안에 자식 페이지 표시 | `<Outlet />`        |

동적 라우팅과 URL 파라미터는 서로 밀접하게 관련되어 있다. Route에서 `:id`처럼 동적으로 변하는 경로를 정의하고, `useParams()`로 실제 값을 가져온다.

반면 쿼리 파라미터는 URL 경로 자체가 아니라 `?` 뒤에 검색이나 정렬 등의 조건을 전달한다.

## 2. useEffect와 useLayoutEffect의 차이

React에서는 컴포넌트 렌더링 이후 특정 작업을 수행하기 위해 `useEffect`와 `useLayoutEffect`를 사용할 수 있다.

두 Hook의 가장 큰 차이는 **브라우저가 화면을 그리는 Paint 시점과 관련하여 언제 실행되는가**이다.

### 2-1. useEffect

`useEffect`는 렌더링 이후 외부 시스템과 동기화하는 작업을 처리할 때 사용하는 Hook이다. 일반적으로 브라우저가 화면을 그린 후 실행되므로 화면 표시를 막지 않고 처리할 수 있는 작업에 적합하다.

```jsx
import { useEffect } from 'react';

useEffect(() => {
  fetchData();
}, []);
```

위 코드는 컴포넌트가 처음 마운트된 이후 Effect를 실행한다. 다만 실제 실행 시점은 렌더링 상황에 따라 달라질 수 있으며, 개발 모드의 Strict Mode에서는 Effect가 추가로 실행되는 경우도 있다.

**주요 활용 사례**

- API 요청 및 데이터 동기화
- 이벤트 등록 및 해제
- 타이머 설정 및 정리
- LocalStorage와 상태 동기화

일반적인 데이터 요청이나 이벤트 처리처럼 화면이 먼저 표시되어도 문제가 없는 작업에 적합하다.

### 2-2. useLayoutEffect

`useLayoutEffect`는 DOM 변경이 반영된 후 브라우저가 화면을 그리기 전에 실행되는 Hook이다. Effect 안에서 수행한 작업과 그로 인한 동기적인 상태 업데이트가 끝날 때까지 브라우저의 화면 그리기가 지연될 수 있다.

```jsx
import { useLayoutEffect } from 'react';

useLayoutEffect(() => {
  // DOM의 크기나 위치를 측정하는 작업
}, []);
```

예를 들어 특정 요소의 높이를 측정한 후 그 값에 따라 위치를 조정해야 한다면, 사용자가 조정 전 화면을 보는 현상을 줄이기 위해 사용할 수 있다.

**주요 활용 사례**

- DOM 요소의 크기 및 위치 측정
- 화면 표시 전에 레이아웃 조정
- 위치 계산이 중요한 팝오버나 툴팁 구현

### 2-3. 두 Hook의 차이

| 구분             | useEffect                                         | useLayoutEffect                                 |
| ---------------- | ------------------------------------------------- | ----------------------------------------------- |
| 실행 시점        | 일반적으로 화면 표시를 막지 않고 실행             | Paint 이전에 실행                               |
| 주요 목적        | 외부 시스템과 동기화                              | DOM 측정 및 화면 표시 전 조정                   |
| 화면 그리기 영향 | 일반적으로 화면 표시를 막지 않음                  | 작업이 끝날 때까지 화면 그리기가 지연될 수 있음 |
| 사용 빈도        | 일반적으로 우선 사용                              | 필요한 경우에 사용                              |
| 주의점           | 시각적 변경이 늦게 반영되면 깜빡임이 보일 수 있음 | 오래 걸리는 작업은 화면 표시를 지연시킬 수 있음 |

**useEffect 실행 흐름**

```text
React 렌더링
    ↓
DOM 변경 반영
    ↓
브라우저 Paint
    ↓
useEffect 실행 (일반적인 경우)
```

**useLayoutEffect 실행 흐름**

```text
React 렌더링
    ↓
DOM 변경 반영
    ↓
useLayoutEffect 실행
    ↓
필요한 동기적 업데이트 완료
    ↓
브라우저 Paint
```

### 2-4. 어떤 Hook을 사용해야 하는가?

기본적으로는 `useEffect`를 먼저 고려한다.

이번 Todo List 프로젝트에서는 `todos`가 변경될 때마다 LocalStorage에 데이터를 저장하기 위해 `useEffect`를 사용했다.

```jsx
useEffect(() => {
  localStorage.setItem('tasks', JSON.stringify(todos));
}, [todos]);
```

`todos`가 변경될 때마다 최신 데이터를 LocalStorage에 저장하므로 새로고침 후에도 데이터를 불러올 수 있다.

반면 DOM의 크기나 위치를 측정한 결과를 Paint 전에 반영해야 하는 경우에는 `useLayoutEffect`를 고려할 수 있다.

정리하면 다음과 같다.

- 일반적인 작업 및 외부 시스템 동기화 → `useEffect`
- Paint 전에 DOM을 측정하거나 화면을 조정해야 하는 작업 → `useLayoutEffect`

특별히 Paint 이전에 작업해야 할 이유가 없다면 `useEffect`를 사용하는 것이 적절하다.

## 3. 브라우저 렌더링 과정

브라우저는 HTML과 CSS를 분석하고, 각 요소의 위치와 크기를 계산한 뒤 실제 화면에 표시한다.

일반적인 렌더링 과정을 개념적으로 정리하면 다음과 같다.

```text
HTML / CSS
    ↓
DOM / CSSOM 생성
    ↓
Render Tree 구성
    ↓
Layout
    ↓
Paint
    ↓
Compositing
    ↓
최종 화면 출력
```

### 3-1. DOM 및 CSSOM 트리 생성

**DOM (Document Object Model)**

브라우저는 HTML을 파싱하여 DOM 트리를 생성한다. DOM은 HTML 문서의 요소와 계층 구조를 객체 형태로 표현한 것이다.

예를 들어 다음 HTML이 있다고 가정한다.

```html
<body>
  <div>
    <h1>Hello</h1>
    <p>World</p>
  </div>
</body>
```

브라우저는 HTML을 분석하여 `body`, `div`, `h1`, `p` 등의 요소를 계층 구조로 표현한다.

개념적으로 다음과 같은 과정을 거친다.

```text
HTML
 ↓
바이트
 ↓
문자
 ↓
토큰
 ↓
노드
 ↓
DOM Tree
```

**CSSOM (CSS Object Model)**

CSSOM은 CSS 규칙을 브라우저가 이해할 수 있는 구조로 표현한 것이다.

브라우저는 CSS를 파싱하여 각 요소에 적용할 스타일 정보를 구성한다.

```text
CSS
 ↓
CSS 파싱
 ↓
CSSOM Tree
```

따라서 이 단계에서는 HTML을 기반으로 한 DOM과 CSS를 기반으로 한 CSSOM이 생성된다.

### 3-2. 렌더 트리(Render Tree) 생성

브라우저는 DOM과 CSSOM의 정보를 이용하여 화면에 표시할 요소와 스타일을 구성한다. 이를 개념적으로 Render Tree 생성 단계라고 한다.

```text
DOM Tree + CSSOM Tree
          ↓
      Render Tree
```

예를 들어 다음 CSS가 적용되어 있다고 가정한다.

```css
.hidden {
  display: none;
}
```

`display: none`이 적용된 요소는 화면에 표시되지 않으므로 일반적인 렌더 트리에서 제외된다.

다만 DOM 자체에서 요소가 삭제되는 것은 아니다. DOM에는 요소가 남아 있지만 화면 표시 대상에서 제외되는 것이다.

### 3-3. Layout (Reflow)

Layout은 화면에 표시할 요소의 위치와 크기를 계산하는 단계이다. 이 과정은 Reflow와 관련이 있다.

주요 계산 대상은 다음과 같다.

- 요소의 위치
- 요소의 너비와 높이
- 요소 간의 배치 관계
- 화면 영역 내에서의 배치

예를 들어 부모 요소의 너비가 변경되면 자식 요소의 크기나 줄바꿈, 주변 요소의 배치도 달라질 수 있다.

```text
Render Tree
    ↓
위치와 크기 계산
    ↓
Layout
```

Layout 단계가 끝나면 각 요소가 화면의 어디에, 어느 정도 크기로 배치될지 계산된다.

### 3-4. Paint (Repaint)

Paint는 요소의 시각적인 모습을 실제로 그리는 단계이다.

주요 대상은 다음과 같다.

- 텍스트
- 색상과 배경
- 이미지
- 테두리
- 그림자

```text
Layout 결과
    ↓
텍스트 / 이미지 / 색상 / 테두리 그리기
    ↓
Paint
```

브라우저는 성능을 최적화하기 위해 화면을 여러 개의 Layer로 나누어 처리할 수 있다. 변경된 영역만 다시 그릴 수 있도록 관리하는 방식도 사용한다.

### 3-5. Compositing

Compositing은 여러 Layer를 적절한 순서로 합쳐 최종 화면을 구성하는 과정이다.

```text
Layer 1
Layer 2
Layer 3
   ↓
Compositing
   ↓
최종 화면
```

레이어를 합성하여 최종 이미지를 화면에 표시한다. 모든 화면 변경이 반드시 DOM부터 Compositing까지 전체 단계를 다시 수행하는 것은 아니며, 변경된 속성과 브라우저의 최적화 방식에 따라 필요한 작업만 수행할 수 있다.

### 3-6. 브라우저 렌더링 과정 정리

| 단계        | 역할                             |
| ----------- | -------------------------------- |
| DOM / CSSOM | HTML과 CSS를 각각 구조화         |
| Render Tree | 화면에 표시할 요소와 스타일 구성 |
| Layout      | 요소의 위치와 크기 계산          |
| Paint       | 텍스트, 색상, 이미지 등을 그림   |
| Compositing | 여러 Layer를 합쳐 최종 화면 구성 |

특히 Layout과 Paint는 화면 변경과 성능을 이해할 때 중요한 개념이다.

예를 들어 요소의 너비나 높이가 변경되면 Layout을 다시 계산해야 할 수 있다. 반면 레이아웃에 영향을 주지 않는 색상 변경은 Paint만 다시 수행할 수 있다.

## 4. Reflow와 Repaint의 차이

브라우저는 DOM이나 CSS가 변경되면 변경된 내용을 화면에 반영해야 한다. 이때 발생할 수 있는 대표적인 작업이 Reflow와 Repaint이다.

- **Reflow**: 요소의 위치와 크기를 다시 계산하는 작업
- **Repaint**: 요소의 시각적인 모습을 다시 그리는 작업

### 4-1. Reflow

Reflow는 DOM 구조나 스타일이 변경되어 요소의 위치와 크기를 다시 계산해야 할 때 발생할 수 있다.

예를 들어 요소의 너비가 변경되는 경우가 있다.

```css
.box {
  width: 100px;
}
```

이후 `width`가 변경되면 요소의 크기와 주변 요소의 배치를 다시 계산해야 할 수 있다.

```text
DOM / CSS 변경
      ↓
레이아웃 재계산
      ↓
Reflow
```

Reflow는 한 요소의 변경이 주변 요소의 배치에도 영향을 줄 수 있기 때문에 상대적으로 비용이 큰 작업이다.

### 4-2. Repaint

Repaint는 요소의 레이아웃은 유지하면서 색상이나 배경 등 시각적인 부분이 변경될 때 발생할 수 있다.

예를 들어 다음과 같이 배경색이 변경되는 경우이다.

```css
.box {
  background-color: blue;
}
```

요소의 위치와 크기는 그대로이고 색상만 변경된다면 레이아웃을 다시 계산하지 않고 변경된 부분을 다시 그릴 수 있다.

```text
시각적 스타일 변경
        ↓
변경된 부분 다시 그리기
        ↓
Repaint
```

일반적으로 Repaint는 Reflow보다 적은 비용이 들지만, 많은 요소를 반복적으로 다시 그리면 성능에 영향을 줄 수 있다.

### 4-3. Reflow와 Repaint 비교

| 구분          | Reflow                            | Repaint                          |
| ------------- | --------------------------------- | -------------------------------- |
| 의미          | 레이아웃 재계산                   | 시각적인 모습 다시 그리기        |
| 주요 원인     | 요소의 크기, 위치, 구조 등의 변경 | 색상, 배경 등 시각적 스타일 변경 |
| 계산 내용     | 위치와 크기                       | 색상, 테두리, 그림자 등          |
| 일반적인 비용 | 상대적으로 큼                     | Reflow보다 작은 편               |
| 예시          | `width`, `height` 변경            | `background-color` 변경          |

핵심적으로 Reflow는 요소가 어디에 어떤 크기로 배치될지를 다시 계산하는 작업이고, Repaint는 계산된 레이아웃을 바탕으로 시각적인 모습을 다시 그리는 작업이다.

### 4-4. 두 작업의 관계

Reflow가 발생하면 변경된 레이아웃을 화면에 반영하기 위해 이후 Paint 작업이 필요할 수 있다.

반면 레이아웃에 영향을 주지 않는 색상 변경은 Reflow 없이 Repaint만 발생할 수 있다.

**레이아웃에 영향을 주는 변경**

```text
레이아웃에 영향을 주는 변경
        ↓
     Reflow
        ↓
필요한 경우 Repaint
        ↓
화면 반영
```

**레이아웃에 영향을 주지 않는 시각적 변경**

```text
레이아웃에 영향을 주지 않는 시각적 변경
        ↓
     Repaint
        ↓
화면 반영
```

단, 실제 브라우저의 렌더링 작업은 변경된 속성이나 브라우저의 최적화 방식에 따라 달라질 수 있다.

## 5. Context API 실습: 삭제 확인 모달 구현

### 5-1. 실습 목적

Todo List 프로젝트에 삭제 확인 모달을 추가하면서 Context API를 활용해 여러 하위 컴포넌트가 모달의 상태와 동작을 공유하도록 구현했다.

삭제 버튼을 누르는 즉시 항목을 삭제하는 대신, 확인 모달에서 사용자가 삭제 여부를 선택하도록 구성했다.

**주요 목표**

- Context API로 모달 상태 공유하기
- `useState`로 모달 열림 상태 관리하기
- Provider와 `useContext`의 역할 이해하기
- 모달 컴포넌트를 역할별로 분리하기
- 기존 Button 컴포넌트 재사용하기

### 5-2. Context 생성하기

`ModalContext.jsx`에서 Context를 생성하고, 하위 컴포넌트가 Context 값을 사용할 수 있도록 커스텀 훅을 작성했다.

```jsx
import { createContext, useContext } from 'react';

export const ModalContext = createContext(null);

export const useModalContext = () => {
  const context = useContext(ModalContext);

  if (!context) {
    throw new Error('Modal 하위 컴포넌트는 Modal 내부에서 사용해야 합니다.');
  }

  return context;
};
```

- `createContext()`는 Context를 생성한다.
- `useContext()`는 상위 Provider가 전달한 값을 가져온다.
- `useModalContext()`는 Context를 사용하는 코드를 재사용할 수 있도록 만든 커스텀 훅이다.

Context를 Provider 외부에서 사용하면 오류를 발생시켜 잘못된 사용을 빠르게 확인할 수 있다.

### 5-3. 모달 상태 관리하기

`Modal.jsx`에서는 `useState`를 이용해 모달이 열려 있는지 관리했다.

```jsx
const [isOpen, setIsOpen] = useState(false);

const openModal = () => setIsOpen(true);
const closeModal = () => setIsOpen(false);
```

그리고 Provider의 `value`로 상태와 함수를 전달한다.

```jsx
<ModalContext.Provider value={{ isOpen, openModal, closeModal }}>{children}</ModalContext.Provider>
```

이렇게 하면 하위 컴포넌트가 각자 모달 상태를 따로 관리하지 않고 공통된 상태와 함수를 사용할 수 있다.

### 5-4. 모달 컴포넌트 분리하기

모달을 하나의 파일에 모두 작성하지 않고 역할별로 분리했다.

| 컴포넌트            | 역할                            |
| ------------------- | ------------------------------- |
| `Modal.jsx`         | 모달 상태 관리 및 Provider 제공 |
| `ModalContext.jsx`  | Context 생성 및 커스텀 훅 제공  |
| `ModalTrigger.jsx`  | 모달을 여는 요소 처리           |
| `ModalContent.jsx`  | 모달 콘텐츠 표시                |
| `ModalClose.jsx`    | 모달을 닫는 동작 처리           |
| `ModalBackdrop.jsx` | 모달 뒤의 배경 표시             |

컴포넌트를 역할별로 분리하면 각 파일이 담당하는 기능을 명확하게 파악할 수 있고, 모달을 사용하는 코드도 읽기 쉬워진다.

### 5-5. Todo 삭제 기능에 적용하기

모달을 구현한 후 Todo 항목의 삭제 버튼에 연결했다.

```jsx
<Modal>
  <Modal.Trigger>
    <Button variant="danger">삭제</Button>
  </Modal.Trigger>

  <Modal.Backdrop />

  <Modal.Content>
    <h2>할 일을 삭제하시겠습니까?</h2>

    <div className="modal-actions">
      <Modal.Close>
        {(closeModal) => (
          <Button variant="secondary" onClick={closeModal}>
            취소
          </Button>
        )}
      </Modal.Close>

      <Modal.Close>
        {(closeModal) => (
          <Button
            variant="danger"
            onClick={() => {
              onDelete(todo.id);
              closeModal();
            }}
          >
            삭제
          </Button>
        )}
      </Modal.Close>
    </div>
  </Modal.Content>
</Modal>
```

**동작 흐름**

1. 사용자가 삭제 버튼을 클릭한다.
2. `openModal()`이 실행된다.
3. 삭제 확인 모달이 표시된다.
4. 취소를 누르면 모달만 닫히고 Todo는 유지된다.
5. 삭제를 누르면 해당 Todo를 삭제하고 모달을 닫는다.

기존 Button 컴포넌트를 재사용하여 버튼 스타일을 일관되게 유지했다.

<button className="px-4 py-2 rounded-md">추가</button>

npm install tailwindcss @tailwindcss/vite

import react from '@vitejs/plugin-react';

export default defineConfig({

### 6-2. ESLint

ESLint는 JavaScript 코드에서 발생할 수 있는 문제나 일관되지 않은 코드 작성 방식을 검사하는 도구이다.

프로젝트의 `eslint.config.js`에 설정된 규칙을 기준으로 코드를 검사한다.

**설정 코드**

```js
import js from '@eslint/js';
import globals from 'globals';
import reactHooks from 'eslint-plugin-react-hooks';
import reactRefresh from 'eslint-plugin-react-refresh';
import prettierConfig from 'eslint-config-prettier';
import { defineConfig, globalIgnores } from 'eslint/config';

export default defineConfig([
  globalIgnores(['dist']),

  {
    files: ['**/*.{js,jsx}'],
    extends: [
      js.configs.recommended,
      reactHooks.configs.flat.recommended,
      reactRefresh.configs.vite,
    ],
    languageOptions: {
      globals: globals.browser,
      parserOptions: {
        ecmaFeatures: { jsx: true },
      },
    },
  },

  prettierConfig,
]);
```

**주요 설정 설명**

| 설정                                  | 역할                                                |
| ------------------------------------- | --------------------------------------------------- |
| `globalIgnores(['dist'])`             | 빌드 결과물인 `dist` 폴더를 검사에서 제외           |
| `js.configs.recommended`              | JavaScript 기본 권장 규칙 적용                      |
| `reactHooks.configs.flat.recommended` | React Hooks 사용 규칙 검사                          |
| `reactRefresh.configs.vite`           | Vite의 Fast Refresh 관련 규칙 적용                  |
| `globals.browser`                     | `window`, `document` 등 브라우저 전역 변수 인식     |
| `ecmaFeatures: { jsx: true }`         | JSX 문법 사용 설정                                  |
| `prettierConfig`                      | Prettier와 충돌할 수 있는 ESLint 포맷 규칙 비활성화 |

**실행 명령어**

```bash
npm run lint
```

ESLint를 사용하면 다음과 같은 부분을 확인할 수 있다.

- 사용하지 않는 변수나 import
- 문법적인 문제
- 잘못된 코드 작성 방식
- React Hooks 사용 규칙 위반

기능을 구현한 후 `npm run lint`를 실행하여 코드에 문제가 없는지 확인할 수 있다.

### 6-3. Prettier

Prettier는 코드를 일정한 형식으로 자동 정리해주는 코드 포맷터이다.

들여쓰기, 줄바꿈, 따옴표 등의 작성 방식을 통일하여 여러 사람이 함께 개발할 때 코드 스타일을 일관되게 유지할 수 있다.

**설정**

`.prettierrc`에 코드 스타일 규칙을 정의했다.

```json
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "all",
  "printWidth": 100,
  "endOfLine": "lf"
}
```

**주요 옵션 설명**

| 옵션                   | 의미                                                 |
| ---------------------- | ---------------------------------------------------- |
| `semi: true`           | 문장 끝에 세미콜론 사용                              |
| `singleQuote: true`    | 문자열에 작은따옴표 사용                             |
| `tabWidth: 2`          | 들여쓰기 2칸                                         |
| `trailingComma: "all"` | 여러 줄로 작성한 목록의 마지막 항목 뒤에도 쉼표 추가 |
| `printWidth: 100`      | 한 줄의 권장 길이를 100자로 설정                     |
| `endOfLine: "lf"`      | 줄바꿈 문자를 LF로 통일                              |

**ESLint와의 연동**

`eslint-config-prettier`를 ESLint 설정 마지막에 추가하여 Prettier와 충돌하는 포맷 관련 규칙을 비활성화했다.

두 도구의 역할은 다음과 같이 구분된다.

- **ESLint**: 코드의 잠재적인 문제와 규칙 위반 검사
- **Prettier**: 코드의 들여쓰기, 줄바꿈, 따옴표 등 형식 정리

따라서 ESLint로 코드의 문제를 검사하고 Prettier로 코드 형식을 통일하는 방식으로 사용할 수 있다.

### 6-4. React Router

React Router는 URL에 따라 서로 다른 React 컴포넌트를 표시할 수 있도록 도와주는 라이브러리이다.

Todo List 프로젝트에서는 할 일 목록, 전체 목록, 완료 목록, 통계 페이지를 분리하기 위해 `react-router-dom`을 설치했다.

**설치**

```bash
npm install react-router-dom
```

**라우팅 설정**

`App.jsx`에서 `BrowserRouter`, `Routes`, `Route`를 사용하여 페이지를 구성했다.

```jsx
import { BrowserRouter, Route, Routes } from 'react-router-dom';
```

각 URL에 따라 다른 페이지가 렌더링되도록 설정했다.

```jsx
<BrowserRouter>
  <Routes>
    <Route path="/" element={<TodoPage {...pageProps} />} />
    <Route path="/all" element={<AllPage {...pageProps} />} />
    <Route path="/completed" element={<CompletedPage {...pageProps} />} />
    <Route path="/stats" element={<StatsPage {...pageProps} />} />
  </Routes>
</BrowserRouter>
```

**페이지별 역할**

| 경로         | 페이지          | 역할                                              |
| ------------ | --------------- | ------------------------------------------------- |
| `/`          | `TodoPage`      | 진행 중인 Todo 표시                               |
| `/all`       | `AllPage`       | 전체 Todo 표시                                    |
| `/completed` | `CompletedPage` | 완료된 Todo 표시                                  |
| `/stats`     | `StatsPage`     | 전체 개수, 진행 중 개수, 완료 개수 및 완료율 표시 |

**상태와 페이지 분리**

Todo 상태와 추가·수정·삭제·완료 처리 함수는 `App.jsx`에서 관리하고, 각 페이지에 props로 전달했다.

```jsx
const pageProps = {
  todos,
  onAdd: handleAdd,
  onToggle: handleToggle,
  onDelete: handleDelete,
  onEdit: handleEdit,
};
```

`{...pageProps}`는 객체에 담긴 속성을 개별 props로 전달하는 문법이다.

이렇게 구성하면 여러 페이지에서 같은 Todo 상태와 기능을 공유할 수 있다. 또한 상태 관리 로직과 실제 화면을 보여주는 페이지 컴포넌트를 분리할 수 있다.

### 6-5. 폴더 구조

React Router를 적용하면서 페이지 컴포넌트를 별도의 `pages` 폴더로 분리했다.

```text
src/
├── components/
│   ├── Button/
│   ├── Card/
│   ├── Checkbox/
│   ├── Input/
│   ├── Modal/
│   ├── Navigation/
│   ├── Text/
│   └── TodoItem/
│
├── pages/
│   ├── TodoPage.jsx
│   ├── AllPage.jsx
│   ├── CompletedPage.jsx
│   └── StatsPage.jsx
│
├── App.jsx
├── App.css
├── index.css
└── main.jsx
```

**폴더 및 파일별 역할**

| 폴더/파일     | 역할                                     |
| ------------- | ---------------------------------------- |
| `components/` | 여러 페이지에서 재사용하는 UI 컴포넌트   |
| `Button/`     | 버튼 UI와 스타일 관리                    |
| `Input/`      | 입력 필드 UI 관리                        |
| `Checkbox/`   | Todo 완료 상태를 표시하는 체크박스       |
| `TodoItem/`   | 하나의 Todo 항목과 관련 기능 표시        |
| `Modal/`      | Context API 기반 합성 모달 컴포넌트      |
| `Card/`       | 통계 수치 등을 표시하는 카드 컴포넌트    |
| `Navigation/` | 할 일 목록과 통계 등 페이지 이동 UI      |
| `pages/`      | URL에 따라 렌더링되는 페이지 컴포넌트    |
